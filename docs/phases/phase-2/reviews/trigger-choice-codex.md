**Recommend A. Keep launch, wake, and display-change events for fast recovery, and add a five-second check while the ledger has a current-boot entry.** The requirement depends on detecting a persistent state: the Mac is awake, a display that `displayctl` disabled can be restored, and the usable active count is zero. A periodic check can detect that state even when the callback stream goes quiet. `docs/phases/phase-2/design.md:115`, `docs/phases/phase-2/design.md:148`

### Why B cannot guarantee recovery

Suppose macOS sends a removal callback while Core Graphics still reports the Dell as active. Every check that B schedules in response can finish before Core Graphics stops reporting the Dell. If macOS sends no further callback, the app has no reason to look again. Any finite settle or follow-up rule has a last sample. To prove B complete would require a guarantee of a callback after the relevant state becomes observable, or a documented upper bound on settling after a delivered callback. The observed placeholder callback several seconds after unplug is another chance to sample. It provides neither guarantee. With D-013’s `unkn` / `virt` / serial `0` filter, a placeholder-only state stays at **zero usable displays** across subsequent polls. `docs/phases/phase-2/design.md:122`, `docs/decisions.md:74`, `docs/decisions.md:80`, `Sources/DisplayControlCore/DisplayInventory.swift:115`

Across the five reviews, I count **six numbered findings about lost or too-early recovery checks**, plus **four about callback timing or replay defeating the retry bound**. These are finding counts, with some races revisited across rounds. The latest review shows both sides clearly. ### Event rules I’d use with A

1. **Treat reconfiguration callbacks as hints.** Ignore begin notifications. The first eligible callback schedules one check after a short settle window, starting with the existing two seconds. Coalesce later callbacks into that pending check without extending its deadline. While recovery is running, drop ordinary callbacks without replay. Remove arrival timestamps, callback-time counts, the `.displayActive` follow-up, and positive-count re-arming. Keep the panel refresh path. If callback registration fails, report that immediate display-change detection is unavailable and leave polling armed. `Sources/DisplayMenuApp/SystemObservers.swift:20`, `Sources/DisplayMenuApp/SystemObservers.swift:42`, `Sources/DisplayControlCore/ZeroActiveRecovery.swift:168`, `Sources/DisplayControlCore/ZeroActiveRecovery.swift:209`
2. **Use one scheduler and one retry budget.** A timer tick samples the cheap usable count. Positive means done, a query error means unknown, and confirmed zero can start the existing guarded episode if idle and outside cooldown. The current count helper maps errors to zero, so expose the error separately for this use. Keep the shared lock and fresh pre-enable check in `recoverIfNoneActive()`. After the three-attempt budget or the inconsistent-sample budget is exhausted, schedule a retry after a finite cooldown, such as 60 seconds. Ordinary callbacks cannot reset or bypass it. Five seconds is the nominal time to **detect** persistent darkness while awake and outside cooldown. It excludes scheduling delays and the time to restore the display. A 60-second cooldown deliberately trades away the design’s ten-second target on the exhausted-retry path. `Sources/DisplayControlCore/DisplayInventory.swift:140`, `Sources/DisplayControlCore/ZeroActiveRecovery.swift:37`, `Sources/DisplayControlCore/ConnectionController.swift:261`, `Sources/DisplayControlCore/ConnectionController.swift:345`, `Sources/DisplayMenuApp/LiveAdapters.swift:86`, `docs/phases/phase-2/design.md:167`
3. **Give launch and wake a prompt settled check.** Always read ledger state at launch. On wake, request one fresh check, coalesced if an episode is running, with a fresh retry budget for that sleep/wake cycle. Keep the guarded active-display reconciliation on wake so it can clear the ledger if macOS already lit the built-in on lid open. Use an ordinary timer with no sleep-prevention assertion and no replay of missed ticks. The recorded lid-closed run ended with macOS lighting the panel on lid open and the wake check finding it active. That makes lid opening the relevant recovery deadline in this case. `Sources/DisplayMenuApp/SystemObservers.swift:29`, `Sources/DisplayControlCore/ConnectionController.swift:261`, `Sources/DisplayControlCore/ConnectionController.swift:415`, `docs/phases/phase-2/design.md:180`

### Cost and verification

At five seconds, an eight-hour docked day can mean **5,760 timer firings** even when the Dell stays active. Each normal tick is an active-list query plus vendor, model, and serial lookups, with no full inventory, I/O Registry walk, or operation lock. The CPU work is small in scope, but timer wakeups can still affect idle power. Use one timer with modest tolerance, avoid logging healthy ticks, and measure wakeups and CPU over a docked idle run. Keep ledger eligibility current across app **and CLI** writes. For example, observe the containing directory, which sees atomic file replacement, and reload on launch, wake, and changes. A timer that starts only after the app sees a display callback would reintroduce the dependency A is meant to remove. `Sources/DisplayControlCore/DisplayInventory.swift:126`, `Sources/DisplayControlCore/DisplayInventory.swift:230`, `Sources/DisplayControlCore/DisabledDisplayLedger.swift:75`, `Sources/DisplayControlCore/ConnectionController.swift:320`, `Sources/DisplayMenuApp/LiveAdapters.swift:12`

With a fake clock, test the core promise directly: the last callback samples a usable Dell, the count later becomes zero with **no further callback**, and the next eligible tick starts recovery. Also test a placeholder-only list, callback bursts during recovery and cooldown, wake after a lid-closed failure, and an empty-to-nonempty ledger written by the CLI. On hardware, disable the event fast path for one undock test and verify that polling alone restores the panel within the normal ten-second target. A gives you a testable recovery property, conditional on the agent being runnable and macOS permitting the enable, without having to establish which operation caused each callback. `docs/phases/phase-2/design.md:159`, `docs/phases/phase-2/design.md:167`, `docs/phases/phase-2/design.md:178`
