## Findings

1. **P2 · Architecture — The blocking-work plan cannot be implemented through the interfaces it specifies.** Task 2 gives recovery synchronous `snapshot()` and `recoverIfNoneActive()` dependencies, then says the app wraps them with an `async` executor. Those synchronous methods cannot await it. Brightness has the inverse problem. The executor takes a synchronous closure, while `DDCBrightnessController.get` and `set` are actor-isolated. Starting a `Task` from the queue would put the blocking I/O and sleeps back on the actor’s executor. Define an awaitable recovery boundary and specify which executor actually runs the DDC work. Preserve the synchronous controller API used by the CLI. [Implementation plan:71](docs/phases/phase-2/implementation-plan.md:71) · [Implementation plan:143](docs/phases/phase-2/implementation-plan.md:143) · [DDC.swift:28](Sources/DisplayControlCore/DDC.swift:28)

2. **P2 · Correctness — Task 2 still promises an extra run for an event received during recovery.** `testTriggerDuringRunSchedulesOneMore` expects two runs without qualifying the trigger or the first outcome. The failed-episode test sends its callback *after* the failure, leaving the original self-triggering sequence untested. The plan also puts the first inventory sample inside the connector, where a sampling error can exhaust the three-attempt budget before the five-sample rule applies. Define how a queued reconfiguration and a queued wake are handled when an episode ends, and how the sample budget applies to the locked check and post-attempt verification. Test a failed enable that emits its callback before returning. The Task 2 filter should include `RecoverySchedulerTests`. [Design:119](docs/phases/phase-2/design.md:119) · [Implementation plan:115](docs/phases/phase-2/implementation-plan.md:115)

3. **P2 · Architecture — An inconclusive inventory can silently disarm the next real undock.** The scheduler treats `.snapshotUnavailable` like a confirmed zero-active failure. If sampling fails during a configuration change and the Dell is usable once the topology settles, there may be no further callback until it is unplugged. That callback sees zero active displays, so it cannot re-arm the scheduler, and the built-in stays off. Preserve a way to recognize a later genuine topology change after an inconclusive episode while keeping recovery-generated callbacks within the original budget. [Design:124](docs/phases/phase-2/design.md:124) · [Implementation plan:94](docs/phases/phase-2/implementation-plan.md:94)

4. **P2 · Correctness — The sequence rule can discard the switch result it was added to protect.** A switch can start with sequence 1, emit a reconfiguration callback, and then fail its postcondition. The callback starts refresh 2, which can publish while the switch is awaiting its follow-up snapshot. The blanket sequence rule can then reject the switch error. Apply ordering to snapshot publication and give the switch completion ownership of its error and busy state. Add the inverse of the existing race test, with a newer refresh publishing before a failed switch completes. [Design:96](docs/phases/phase-2/design.md:96) · [Implementation plan:189](docs/phases/phase-2/implementation-plan.md:189)

5. **P2 · Architecture — The fresh UUID lookup still leaves a wrong-monitor write path.** Task 5 resolves the UUID in a snapshot and passes the resulting `Display` to DDC. `set` resolves a service for its preliminary read and resolves again for the write, using metadata fetched from the runtime ID each time. If that ID is reused between read and write, the second resolution can select the replacement monitor. The app queue cannot serialize hardware changes. Bind the write to a validated endpoint or revalidate identity at the transport boundary, including retries. The current held-write test exercises coalescer invalidation and never reaches this path. 6. **P2 · Correctness — Task 4 leaves slider submissions unordered at the UI boundary.** The slider calls synchronous `PanelModel.setBrightness`, which forwards to an actor. If each update starts an independent task, the actor can receive an earlier drag value after the release value. The coalescer tests submit values in order and would pass in that case. Specify ordered delivery from the slider to the coalescer and test that the released value wins through the model entry point. 7. **P2 · Architecture — The new fallback can expire without recovering a display.** The proposed timer runs `connect all` once. It can lose the same lock to a recovery attempt and exit after roughly one second. A two-active-display dry run also cannot establish that the detached process can restore a ledger-only panel in the GUI session. Phase 1’s watchdog confirms readiness and retries until restoration is verified or a hard deadline passes. Reuse those guarantees for the Phase 2 fallback and verify the recovery path before relying on it for zero-active tests. 8. **P2 · Correctness — The hardware sequence can pass without exercising startup or wake recovery.** Step 6 leaves the built-in off and step 8 leaves the app stopped, yet step 9 starts by turning the built-in off from the panel. Step 10 starts its five-second timer before manual setup, so launch can occur with the Dell still active and the later unplug callback can do the recovery. Step 11 can likewise pass through a reconfiguration callback without proving that wake reached the scheduler. 9. **P3 · Architecture — Recovery re-arming adds duplicate full inventory work.** On reconfiguration after an exhausted episode, the observer refreshes the model while the scheduler separately samples for an active display. A full inventory gathers AppKit names and probes DDC capability for external displays. Both calls run on the queue needed by recovery, including while the panel is closed. Use a lightweight topology sample for the scheduler or share the same topology observation for refresh and re-arm. Keep the authoritative zero-active check under the operation lock. 10. **P3 · Correctness — The slider plan has an open hook and leaves the closed state unspecified.** The design requires reads for newly eligible sliders while the panel is open. Task 4 says to read when a refresh makes a row eligible, Task 5 refreshes on background events, and the model has no close signal. A Dell plug while the panel is hidden can cause an unnecessary DDC read, followed by a repeat on reopen. Specify the visibility boundary and test that a row becoming eligible while closed gets its read on reopen.
