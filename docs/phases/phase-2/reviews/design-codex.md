I found one P1. Recovery checks for zero active displays before acquiring the shared operation lock, so it can turn displays back on after the zero-active condition has ended. The launchd and SwiftUI approach is plausible on the target Mac, with the spike needed to establish how the installed app behaves.

## Findings

1. **P1 · architecture — The zero-active check is outside the operation lock.** Recovery samples the inventory, then calls `connectAll()`. While recovery waits for the lock, a CLI `connect` can restore one display. `connectAll()` then acquires the lock, sees the new topology, and still enables other inactive or ledger-only displays. That violates the explicit requirement to preserve the owner’s choices while any display is active. Add a recovery-specific entry point that checks for zero active displays under the same lock as candidate selection and mutation. Preserve the CLI’s unconditional `connect all` behavior. This closes the race between cooperating callers. Test a CLI connect winning the lock and verify that recovery leaves the other displays off. [Phase 2 design.md:111](docs/phases/phase-2/design.md:111) · [ConnectionController.swift:248](Sources/DisplayControlCore/ConnectionController.swift:248)

2. **P2 · correctness — The recovery plan tests the wrong failure channel and leaves part of the spec contradictory.** A corrupt ledger produces a returned `DisplayConnectionOutcome` with `display == nil` and a failed result. Candidate failures, including earlier-boot refusals, are also returned as outcomes. The proposed test makes the connector throw, and the implementation step only specifies logging throws. An implementation could pass the test and omit the real diagnostic D-008 needs. Specify and test both returned failures and thrown errors, including partial recovery. Update the design and its test matrix together. Task 2 amends the ledger precondition, while the design’s empty-ledger test still expects a no-op even when an online inactive display could be restored. [Phase 2 implementation-plan.md:54](docs/phases/phase-2/implementation-plan.md:54) · [Phase 2 implementation-plan.md:105](docs/phases/phase-2/implementation-plan.md:105) · [Phase 2 design.md:144](docs/phases/phase-2/design.md:144) · [ConnectionController.swift:246](Sources/DisplayControlCore/ConnectionController.swift:246)

3. **P2 · architecture — The retry budget is per run, and recovery can schedule another run itself.** The observer treats every post-configuration callback as a new trigger, and the scheduler promises an extra run after a trigger during recovery. An enable transaction can emit a callback and then fail Phase 1’s active-display postcondition. That callback can start a fresh three-attempt run, defeating the promised stop after bounded retries. In the other direction, five immediate inventory retries can all hit the same unstable topology. Define what starts a new recovery episode, how recovery-generated callbacks affect its budget, and when a failed snapshot gets another sample. Test that a failed enable with a callback eventually stops. [Phase 2 design.md:111](docs/phases/phase-2/design.md:111) · [Phase 2 implementation-plan.md:91](docs/phases/phase-2/implementation-plan.md:91) · [Phase 2 implementation-plan.md:113](docs/phases/phase-2/implementation-plan.md:113) · [ConnectionController.swift:368](Sources/DisplayControlCore/ConnectionController.swift:368)

4. **P2 · architecture — The execution and refresh boundaries are incomplete for Swift 6.** `Task.detached` can keep a synchronous call off the main actor, but it still uses Swift’s cooperative executor. The controller sleeps while waiting for `flock`, and the live inventory combines Core Graphics and I/O Registry work with `NSScreen` access. Meanwhile, opening the panel, completing a switch, and receiving several callbacks can all start refreshes. `@MainActor` serializes publication but does not order results across `await`. An older refresh can overwrite the verified post-switch state or clear its error because the plan gives all `refresh()` calls reopen semantics. Specify where blocking work runs, where AppKit screen data is collected, and which results may update the model. A deterministic test can hold an old refresh open until a newer operation completes, then verify that the old result cannot replace the current rows or error. [Phase 2 implementation-plan.md:158](docs/phases/phase-2/implementation-plan.md:158) · [Phase 2 implementation-plan.md:183](docs/phases/phase-2/implementation-plan.md:183) · [Phase 2 implementation-plan.md:257](docs/phases/phase-2/implementation-plan.md:257) · [ConnectionController.swift:61](Sources/DisplayControlCore/ConnectionController.swift:61) · [DisplayInventory.swift:224](Sources/DisplayControlCore/DisplayInventory.swift:224)

5. **P2 · architecture — Observer registration is part of the safety net and has no failure policy.** `CGDisplayRegisterReconfigurationCallback` is a C callback registration that returns `CGError`. The plan does not say how to handle failure, own the `userInfo` context for the app’s lifetime, or hand off asynchronously to Swift isolation. Wake registration also needs `NSWorkspace.shared.notificationCenter`. If registration fails silently, switches can still disable the built-in panel while undock recovery has lost its trigger until wake or relaunch. Specify callback ownership and an observable failure path. A short-lived callback should hand work off to the scheduler and model. Verify that the installed agent receives the last-display removal event with the panel closed. [Phase 2 design.md:104](docs/phases/phase-2/design.md:104) · [Phase 2 implementation-plan.md:257](docs/phases/phase-2/implementation-plan.md:257)

6. **P2 · architecture — Dropping a brightness coalescer does not invalidate pending writes.** Task 4 drops the coalescer when its UUID row goes away, but work already running can retain it and its pending value. If that work captures the old `Display`, the Phase 1 resolver reads metadata from its runtime ID at execution time and does not verify that the ID still belongs to the same UUID. A queued value can outlive a disconnect and, after ID reuse, target a replacement monitor. Specify ordered submission and invalidate pending writes and late results when a display leaves or becomes inactive. Resolve the current active target by UUID at dispatch. Test an unplug or disable while one write is held and another is pending. 7. **P2 · correctness — A display can gain a slider without getting a brightness read.** Brightness loads only on panel appearance. If the owner turns an external display on with the panel open, or plugs one in, the refreshed rows can gain a slider that stays at `—` and the fallback position despite working DDC. Load brightness when a row becomes eligible while the panel is open. Also guard the percentage conversion at the adapter boundary. Phase 1’s parser can return `maximum == 0`, and `get` forwards it, so the planned division can trap instead of showing a read error. Test both a newly eligible row and a zero-maximum reply. 8. **P2 · architecture — The corrupt-ledger message leads directly to discarding recovery data.** The proposed message tells the owner to run `displayctl forget all`. D-005 identifies the ledger as the only route to displays the OS has dropped, and `forget all` overwrites it with an empty file even if loading failed. A decode error or read failure can be repairable, and clearing the file can leave an already-disabled panel unreachable through `connect all`. Surface the failure and preserve the file for diagnosis. Document reset as a deliberate recovery decision after accounting for any displays still off. 9. **P2 · correctness — Hardware validation relies on an unverified fallback at the point of greatest risk.** The critical test intentionally removes the only active display and names replugging the Dell as recovery. Establish a fallback independent of the agent under test, such as a delayed `connect all` verified to reach the GUI session.
