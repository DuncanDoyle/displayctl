### Findings

1. **P1 · architecture · #2 — An undock can still be lost after a lock timeout.** A lock timeout increments `attempts`. If the next locked check sees the Dell active and returns `nil`, the episode ends `.recovered` even though recovery never enabled a display. An unplug between that check and the episode’s completion gets dropped because the follow-up is reserved for `.displayActive`. If that is the only callback, the built-in stays dark. `Sources/DisplayControlCore/ZeroActiveRecovery.swift:77`, `Sources/DisplayControlCore/ZeroActiveRecovery.swift:87`, `Sources/DisplayControlCore/ZeroActiveRecovery.swift:230`

2. **P1 · correctness · #6 — A placeholder ledger entry can still reach the hardware after its runtime ID changes.** The new holder check correctly blocks the placeholder at the *saved* ID, even when its UUID matches. If that same placeholder UUID is now at ID 13 and the ledger says ID 12, both ownership checks can pass when ID 12 is unclaimed. Reconnect then sends an enable to ID 12. If the hardware call returns success, verification accepts the already-active placeholder at ID 13 by UUID and removes the entry. The hardware record shows the same placeholder UUID at both IDs, while the new tests use matching saved and live IDs. `Sources/DisplayControlCore/ConnectionController.swift:350`, `Sources/DisplayControlCore/ConnectionController.swift:366`, `Sources/DisplayControlCore/ConnectionController.swift:448`, `Tests/DisplayControlCoreTests/ConnectionControllerTests.swift:316`, `docs/decisions.md:75`

3. **P2 · architecture · #2 — The extra-episode rule does not preserve the intended bound on callbacks caused by recovery.** Each `.displayActive` episode can schedule a follow-up, and that follow-up has the same rule. The premise is that `.displayActive` issued no enable, but the controller tracks successful reconnects. An enable can reach hardware and fail its postcondition, then the next candidate can see an active display and make the connector return `nil`. The scheduler can therefore start another episode from its own enable callback. The new test ends the follow-up with `.recovered`, so it leaves this path uncovered. `Sources/DisplayControlCore/ConnectionController.swift:268`, `Sources/DisplayControlCore/ConnectionController.swift:297`, `Sources/DisplayControlCore/ConnectionController.swift:425`, `Sources/DisplayControlCore/ZeroActiveRecovery.swift:225`, `Tests/DisplayControlCoreTests/ZeroActiveRecoveryTests.swift:193`

4. **P2 · architecture · #5 — The Perl alarms cap individual commands, and the hard deadline still overruns.** With the default `SIGALRM` disposition, the alarm survives `exec` and limits the direct command. The loop still runs both `list` calls before checking the deadline and can start a 20-second `connect all` when `t` is already at the deadline. The Phase 1 watchdog caps each command by the remaining budget. Readiness now requires a successful `list`, but the parent waits about two seconds for a probe allowed ten. A slow successful probe can leave a detached fallback running after the caller reports startup failure. `Scripts/menu-fallback.sh:40`, `Scripts/menu-fallback.sh:59`, `Scripts/menu-fallback.sh:65`, `Scripts/menu-fallback.sh:95`, `Scripts/menu-fallback.sh:131`, `Scripts/hardware-test.sh:109`

5. **P2 · correctness · #7 and #8 — The docs still describe different recovery and acceptance rules.** The signature, app-only name lookup, usable count, and five-second kickstart updates match the code. Design §6.3 and Task 2 still describe dropping every in-episode trigger and omit the all-throw `.inconclusive` path. The README says the safety net turns nothing on while a usable display is active, but a recovery that starts at zero can continue enabling other candidates after its first success. The hardware record marks step 9 passed without flagging HDMI as pending, and the general ten-second app-restoration requirement still conflicts with the accepted lid-open route for step 11. `docs/phases/phase-2/design.md:122`, `docs/phases/phase-2/design.md:167`, `docs/phases/phase-2/design.md:180`, `docs/phases/phase-2/implementation-plan.md:79`, `README.md:73`, `README.md:241`, `docs/phase-status.md:22`
