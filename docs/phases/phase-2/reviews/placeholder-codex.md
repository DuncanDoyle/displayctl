**No P1 findings. Two P2 findings.** `DisplayInventory` is the right place to classify the macOS placeholder. D-012 should preserve Core Graphics identity and consistency checks while giving the panel, CLI, disconnect guards, and recovery scheduler one shared definition of an active, usable display.

1. **P2 · Architecture · Filtering before validation weakens runtime-ID ownership checks.** Phase 1 requires two checks before reusing an offline ledger entry’s saved ID: no other online UUID holds the ID, and a fresh direct Core Graphics lookup reports no different owner. Both reconnect and rollback get the first check from the snapshot. If D-012 removes an online placeholder that holds the saved ID, the first check loses that owner. The direct lookup still blocks the enable when it returns the placeholder UUID, but `nil` currently permits the enable. Preserve raw online ownership for reconnect and rollback, and run the raw active-subset and per-ID activity checks before projecting the usable displays. Use that same validated sample for the CLI’s placeholder note so the note and stdout describe the same topology. D-005 still requires the target UUID to be present and active after an enable. 2. **P2 · Correctness · The scheduler still counts the placeholder when re-arming.** The live scheduler reads a raw `CGGetActiveDisplayList` count outside `DisplayInventory`. After a failed episode, a reconfiguration while the placeholder is the sole active ID can re-arm the scheduler without running recovery. The next placeholder-only callback can then start another episode during the same dark period, defeating the documented retry boundary. Use the inventory classifier for this count too. A cheap ID-and-properties read is sufficient. Verify that a placeholder-only callback leaves recovery disarmed and that a Dell replug followed by another undock re-arms it. [LiveAdapters.swift](Sources/DisplayMenuApp/LiveAdapters.swift:105) · [ZeroActiveRecovery.swift](Sources/DisplayControlCore/ZeroActiveRecovery.swift:190) · [Phase 2 design §6.3](docs/phases/phase-2/design.md:130)

3. **P3 · Correctness · The signature has one positive hardware sample and no negative controls.** `unkn` / `virt` and 0×0 mm describe generic properties, with no demonstrated exclusivity to the macOS placeholder. There is no observed collision here for Sidecar, AirPlay, DisplayLink, or BetterDisplay/`CGVirtualDisplay`. If an active usable display matches, it disappears from the panel and CLI and can cause unsolicited recovery. If another macOS version changes the signature, the original failure returns. Treat the tuple as a heuristic for the tested system. Check the observed lack of a current mode as a possible corroborating signal, and capture the properties of any virtual displays in use. The repeated UUID is useful in the trace, but its stability across Macs and OS releases is unverified. Keep `isMain` as reported by Core Graphics. The current consumers only serialize it, so the visible rows can all have `main=false`. Include a mirrored configuration in the checks, since Core Graphics can report a hardware mirror online but inactive and an `NSScreen` match is therefore unsuitable as a requirement for every usable display. 4. **P3 · Correctness · The hardware test needs to prove recovery with the placeholder already main.** The transaction targets the saved display ID and has no main-display dependency in code. The private API’s behavior in this topology is still unverified. The reported six seconds measures placeholder appearance, so it does not justify increasing the two-second settle window. An unplug callback can lead to recovery before the placeholder appears. Conversely, if the Dell still counts as active at the first locked check, the episode returns `displayActive` and needs a later trigger. Timestamp unplug, completed callbacks, the first usable-zero sample, each enable attempt, and the built-in becoming visibly usable. Keep the ten-second acceptance limit measured from the event.
