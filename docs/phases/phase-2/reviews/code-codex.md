**Phase 2 Tasks 2–6 have P1 and P2 findings.** The shared lock closes the race with a cooperating CLI command. Two safety-net bugs remain: a hardware change can invalidate the zero-active check before recovery enables anything, and the scheduler can miss the event that should re-arm it for the next undock.

## P1 findings

1. **P1 · correctness · Recovery can enable a display after another display has become active.** `recoverIfNoneActive()` checks for zero under the lock, then loads the ledger and takes another snapshot to select candidates. If a monitor becomes active between those snapshots, candidate selection sees it and still proceeds with other inactive or ledger-only displays. The lock excludes the CLI, but hardware changes can still occur. This violates design §§3 and 7 before recovery has made its first enable. The CLI’s unconditional `connect all` should retain its current behavior. [ConnectionController.swift:251](Sources/DisplayControlCore/ConnectionController.swift:251) · [ConnectionController.swift:269](Sources/DisplayControlCore/ConnectionController.swift:269)

2. **P1 · correctness · The re-arm debounce can lose the next undock.** After a failed episode, plug the Dell back in, let it become active, then unplug it before the two-second window expires. The unplug resets the timer. The only count runs after the unplug, sees zero, and leaves recovery disarmed. The built-in stays off until another qualifying event. The test settles the plug and unplug separately, so it misses this sequence. Re-arming needs to preserve an observation that a display became active across the debounce window. [ZeroActiveRecovery.swift:154](Sources/DisplayControlCore/ZeroActiveRecovery.swift:154) · [ZeroActiveRecoveryTests.swift:206](Tests/DisplayControlCoreTests/ZeroActiveRecoveryTests.swift:206)

3. **P1 · correctness · A reopen read can leave the slider showing the wrong brightness after the final write succeeds.** Hold a write at 10%, submit 45%, then close and reopen the panel. The reopen read can observe 10% before the pending 45% write reaches DDC. It receives a newer token than the slider submission and publishes 10%. The successful 45% write updates only the error, so the slider and label can stay at 10% while the monitor is at 45%. Order reopen reads with outstanding writes for that UUID. [PanelModel.swift:149](Sources/DisplayMenuKit/PanelModel.swift:149) · [PanelModel.swift:184](Sources/DisplayMenuKit/PanelModel.swift:184)

## P2 findings

4. **P2 · architecture · The live observer drops events based on delivery time, while the design specifies arrival time.** The C callback enqueues a main-actor task, which enqueues another task to reach the scheduler. A callback emitted during an episode can reach `trigger` after `running` has cleared. After `.inconclusive`, that delayed callback can start a fresh episode. The self-trigger test awaits `scheduler.trigger` inside the connector and therefore guarantees delivery before the episode can finish. The process-lifetime retain and nonisolated C handoff are sound. The missing piece is preserving which episode was running when the event arrived. [SystemObservers.swift:39](Sources/DisplayMenuApp/SystemObservers.swift:39) · [ZeroActiveRecovery.swift:154](Sources/DisplayControlCore/ZeroActiveRecovery.swift:154) · [ZeroActiveRecoveryTests.swift:169](Tests/DisplayControlCoreTests/ZeroActiveRecoveryTests.swift:169)

5. **P2 · architecture · The app introduces a stale-target window before DDC starts.** `LiveBrightness` resolves the UUID on the dispatch queue, then hands a `Display` to the DDC actor. That actor can be busy with a panel read or another display’s write. If the runtime ID is reassigned during the wait, the transport’s first resolution can already use the replacement’s serial, vendor, and product. The owner accepted the narrower race *inside* Phase 1’s `set`. The new wait before entering `set` also weakens §6.2’s queued-write guarantee. The held-write test covers coalescer invalidation, while the first DDC resolution remains untested. [LiveAdapters.swift:74](Sources/DisplayMenuApp/LiveAdapters.swift:74) · [DDC.swift:229](Sources/DisplayControlCore/DDC.swift:229) · [design2-codex.md:57](docs/phases/phase-2/reviews/design2-codex.md:57)

6. **P2 · architecture · The CLI falls outside the blocking-work boundary.** The app’s inventory, ledger and connection work uses the serial queue and continuations. Its main actor suspends while awaiting that queue, and the C callback returns asynchronously, so I found no synchronous wait cycle in the current app. The CLI’s async methods still call blocking core operations directly. The newly shared name lookup can now synchronously wait for main from the CLI’s cooperative executor, including while holding the operation lock. The CLI’s async top-level entry point gives main a way to service the hop, and the author observed `list` working. This is an execution-boundary mismatch, with no demonstrated CLI deadlock. [main.swift:92](Sources/displayctl/main.swift:92) · [DisplayInventory.swift:238](Sources/DisplayControlCore/DisplayInventory.swift:238) · [implementation-plan.md:19](docs/phases/phase-2/implementation-plan.md:19)

7. **P2 · correctness · Reinstall modifies the live deployment before validating its replacement.** The script copies both binaries over their installed paths before booting out the old job. It also writes the live plist before linting it. A home path containing `&`, for example, is interpolated as `sed` replacement syntax and can leave a broken executable path in the plist. An interrupted copy or failed render can leave a partial deployment. Stage the binaries, write the path as a plist string, and lint the staged plist before replacing installed files. The `bootout`/`bootstrap` domains and the plist’s clean-exit versus crash policy match the design on inspection. [install-menu.sh:17](Scripts/install-menu.sh:17) · [uninstall-menu.sh:9](Scripts/uninstall-menu.sh:9) · [LaunchAgent plist:5](Scripts/com.github.duncandoyle.displayctl-menu.plist:5)

8. **P2 · correctness · The branch contains workstation paths in committed review documents.** The newly added Phase 1 fix review and both Phase 2 design reviews contain absolute checkout links. The scripts and plist template derive installation paths at runtime. The disclosure is in the review files and their commits, the same publishing issue addressed by D-007. ## Lower-priority findings

- **P3 · correctness · The inverse switch race test never rejects the switch’s snapshot.** It publishes the competing refresh while `disconnect` is suspended. The switch requests its follow-up snapshot afterward and gets a higher sequence number. The implementation correctly gives the switch independent ownership of busy state and error. To cover that behavior, hold the switch’s follow-up snapshot, publish a later refresh, then release the older snapshot and assert the winning rows, switch error and cleared busy state. [PanelModelTests.swift:126](Tests/DisplayMenuKitTests/PanelModelTests.swift:126) · [PanelModel.swift:86](Sources/DisplayMenuKit/PanelModel.swift:86)
- **P4 · architecture · Phase 3 brightness ordering remains a tracked carry-over.** The DDC actor serializes individual operations, while pending slider intent lives in `PanelModel`. A key-driven read/adjust/write could complete and then be overwritten by a previously submitted slider value. Both producers will need a shared ordering boundary when keys land. [PanelModel.swift:174](Sources/DisplayMenuKit/PanelModel.swift:174) · [phase-status.md:38](docs/phase-status.md:38)
