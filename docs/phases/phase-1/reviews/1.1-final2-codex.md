## New findings

1. **P1 · correctness — Brightness SET can report success after the required second send fails.** The Dell over USB-C ignored a single SET on hardware. If the first I2C write returns success and the second fails before delivery, `try?` discards the only error. The controller skips its retry, and the CLI prints the requested percentage and exits 0 even though brightness can stay unchanged. The new unit test explicitly expects success on a second-write timeout, which covers the monitor that accepts one send and also permits this false success. [DDC.swift:830](/Sources/DisplayControlCore/DDC.swift:830) · [DDC.swift:84](/Sources/DisplayControlCore/DDC.swift:84) · [main.swift:185](/Sources/displayctl/main.swift:185) · [DDCTests.swift:560](/Tests/DisplayControlCoreTests/DDCTests.swift:560) · [DDCTests.swift:578](/Tests/DisplayControlCoreTests/DDCTests.swift:578)

2. **P2 · correctness — An unreadable ledger now blocks kind-based recovery of an online display.** At `61333d2`, `connect internal` could enable a unique online inactive panel without reading the ledger first. The new path always loads the ledger before considering that panel. Failing closed preserves ambiguity protection when ledger contents are unknown, but the resulting error gives no recovery route. The same online display remains reachable by its explicit UUID or runtime ID, and `connect all` still attempts online recovery. [ConnectionController.swift:171](/Sources/DisplayControlCore/ConnectionController.swift:171) · [ConnectionController.swift:206](/Sources/DisplayControlCore/ConnectionController.swift:206) · [ConnectionController.swift:240](/Sources/DisplayControlCore/ConnectionController.swift:240)

3. **P2 · correctness — Conflicting ledger records for one UUID are resolved by file order.** The decoder accepts an array with duplicate UUIDs. For two offline records of the same kind and UUID with different saved runtime IDs, the kind path keeps the first and can attempt its ID if the boot and ownership checks pass. The explicit UUID path rejects the same records as ambiguous. Deduplicating identical records is safe, but conflicting recovery identities need to fail before mutation. [DisabledDisplayLedger.swift:59](/Sources/DisplayControlCore/DisabledDisplayLedger.swift:59) · [ConnectionController.swift:183](/Sources/DisplayControlCore/ConnectionController.swift:183) · [ConnectionController.swift:210](/Sources/DisplayControlCore/ConnectionController.swift:210) · [ConnectionController.swift:314](/Sources/DisplayControlCore/ConnectionController.swift:314)

4. **P2 · correctness — The selector docs omit what counts as a match for `connect`.** With one active external display and one inactive external display, `connect external` now enables the inactive display. The design says a kind selector requires exactly one matching display, then describes state validation as a separate step. The README uses the same uniqueness wording. Document the command-specific candidate pool so users with multiple monitors can predict when `connect external` acts and when it reports ambiguity. [ConnectionController.swift:201](/Sources/DisplayControlCore/ConnectionController.swift:201) · [design.md:114](/docs/phases/phase-1/design.md:114) · [README.md:70](/README.md:70)
