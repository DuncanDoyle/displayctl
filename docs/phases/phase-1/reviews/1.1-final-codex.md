**Request changes before closing sub-phase 1.1.** The hardware evidence confirms recovery of dropped internal and external displays on macOS 27.0.1. The review found four correctness bugs involving watchdog recovery, kind selection, disconnect verification, and DDC writes.

## Findings

1. **P1 · architecture — Foreground recovery can still verify before a disconnect commits.** The watchdog starts `displayctl` before publishing its PID. If it dies between those operations, or publishing the record fails, `quiesce_worker` has no PID to wait for. The foreground can see both screens active, report recovery, and then have the orphaned worker commit the disable. The worker needs to wait for successful publication before it can mutate displays. This matters more after D-006 because the watchdog and ledger now carry the recovery guarantee. [hardware-test.sh:161](/Scripts/hardware-test.sh:161) · [hardware-test.sh:468](/Scripts/hardware-test.sh:468)

2. **P1 · correctness — `connect external` can select the wrong display or miss a disabled one.** With external A online and external B in the ledger only, the online match wins before the ledger is consulted. If A is inactive, the command enables A. If A is active, it returns “already active” and leaves B dark. Both outcomes violate the documented rule that a kind selector requires a unique match. Resolve kind selectors across both sources, deduplicate by UUID, and report ambiguity before attempting a mutation. The new test covers only a single ledger match with no same-kind online display. [ConnectionController.swift:171](/Sources/DisplayControlCore/ConnectionController.swift:171) · [README.md:70](/README.md:70) · [ConnectionControllerTests.swift:354](/Tests/DisplayControlCoreTests/ConnectionControllerTests.swift:354)

3. **P1 · correctness — An inconsistent refresh can turn a failed disable into success.** Native disable or commit errors still propagate, and a target that remains visibly active still fails verification. The new false-success path is a transaction that returns success without disabling the target, followed by a refresh during a topology change. If the online sample omits the target and the separately queried active sample contains it, inventory drops the active evidence because it builds rows only from online IDs. D-005 then treats the missing UUID as a verified disconnect. Reject or resample inconsistent inventory before using absence as proof. A genuinely unplugged display satisfies D-005’s state check. [ConnectionController.swift:327](/Sources/DisplayControlCore/ConnectionController.swift:327) · [ConnectionController.swift:341](/Sources/DisplayControlCore/ConnectionController.swift:341) · [DisplayInventory.swift:33](/Sources/DisplayControlCore/DisplayInventory.swift:33) · [DisplayInventory.swift:82](/Sources/DisplayControlCore/DisplayInventory.swift:82)

4. **P1 · correctness — A redundant DDC write can make a working brightness command fail.** On a monitor that accepts the first SET, an error on the second packet 10 ms later fails the exchange. A retryable error repeats the pair, so a monitor that consistently rejects the quick duplicate can change brightness and still make the CLI exit nonzero. GET likewise discards the opportunity to read a valid first reply if the second write fails. The HDMI run predates both repeat commits. The USB-C run validates the workaround on the Dell. Repeating the current absolute luminance value is idempotent, but the generic `writeVCP` method applies the same policy to any code. Keep that policy scoped to the operation that needs it before reusing the transport for a non-idempotent SET. [DDC.swift:812](/Sources/DisplayControlCore/DDC.swift:812) · [DDC.swift:831](/Sources/DisplayControlCore/DDC.swift:831) · [phase-status.md:60](/docs/phase-status.md:60)
