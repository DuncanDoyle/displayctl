**Amend Phase 1.1 before implementation.** The ledger makes a second recovery attempt possible. The design still permits that attempt to target the wrong display, and the watchdog can stop protecting the test while a display is still disabled. The HDMI recovery path remains unverified on macOS 27.0.1.

## P1 findings

1. **P1 · architecture — A saved runtime ID can enable the wrong display.** §6.3.1 explicitly retries entries from earlier logins and boots, even though §6.1 says runtime IDs can change. The bridge accepts only a numeric ID, and the controller checks the UUID after the mutation. If display A disappears and macOS assigns its ID to display B, the command can enable B and then report failure for A. A replug can invalidate the mapping within the same login. Resolve by current UUID first, use the current ID when that UUID is present, and require positive current identity evidence before any offline enable. Apply the same rule to immediate rollback. If identity cannot be established, keep a diagnostic and skip the mutation. [design.md:110](/docs/phases/phase-1/design.md:110) · [design.md:149](/docs/phases/phase-1/design.md:149) · [ConnectionController.swift:170](/Sources/DisplayControlCore/ConnectionController.swift:170) · [ConnectionController.swift:204](/Sources/DisplayControlCore/ConnectionController.swift:204)

2. **P1 · architecture — Confirmation can disarm recovery before restoration.** The brief cancels the watchdog when the user confirms they can see a display. The script then waits for more input before reconnecting the disabled display. If the remaining screen goes dark during that gap, the script is blocked in `read` and its exit trap has no reason to run. Keep recovery armed until the test’s display changes are verified restored. On expiry, restore without input, end the disruptive sequence, and require a fresh opt-in before another disconnect. [design.md:282](/docs/phases/phase-1/design.md:282) · [phase-1.1-brief.md:26](/docs/phases/phase-1/phase-1.1-brief.md:26) · [hardware-test.sh:76](/Scripts/hardware-test.sh:76) · [hardware-test.sh:172](/Scripts/hardware-test.sh:172)

3. **P1 · architecture — The watchdog can fire and exhaust its only recovery attempt.** `disconnect` holds the same lock `connect all` needs across the synchronous Core Graphics transaction and postcondition check. If the disconnect still holds the lock at 20 seconds, the watchdog’s command can time out on lock acquisition about a second later, while the original worker can still complete the disable. A watchdog for session-scoped tests needs a ready signal before mutation, an independent lifetime in the same GUI session, and a bounded way to stop or wait out the mutation worker and verify restoration. A one-shot command at the deadline leaves this race open. ## P2 findings

4. **P2 · architecture — Offline enable is plausible, but the design has no feasibility gate for the failure that prompted it.** The June HDMI run predated the immediate saved-ID retry. Logout/login was also untested. An ID missing from the online list could still name an object WindowServer can configure, or the private call could reject it or complete without restoring output. Both the ledger and the watchdog depend on that same enable path. First validate a bounded `kCGConfigureForAppOnly` trial on macOS 27.0.1: a short-lived helper owns the transaction, and an independent deadline ends it without keyboard input. Quartz documents app-exit reversion for display configuration. Verify that it applies to this private enable operation on normal exit and forced termination, including when the display vanishes from the online list. Use a separate guarded `.forSession` check for the production reconnect path and its logout/login fallback. If neither safe route is established for HDMI, refuse that session-scoped disconnect and leave the Phase 1 external-disconnect criterion open. [codex-handoff-2026-06-30.md:43](/docs/phases/phase-1/codex-handoff-2026-06-30.md:43) · [codex-handoff-2026-06-30.md:55](/docs/phases/phase-1/codex-handoff-2026-06-30.md:55) · [phase-status.md:53](/docs/phase-status.md:53) · [phase-1.1-brief.md:31](/docs/phases/phase-1/phase-1.1-brief.md:31) · [Apple Quartz display transactions](https://developer.apple.com/library/archive/documentation/GraphicsImaging/Conceptual/QuartzDisplayServicesConceptual/Articles/DisplayTransactions.html)

5. **P2 · architecture — The ledger needs a defined location and lifetime.** “Per-user” and “survives process exit” leave open whether the CLI, watchdog, and later login agent share the same file and lock. The current lock defaults to the process’s temporary directory. Specify one private per-user location independent of the working directory and temporary-directory environment, with the ledger and its stable lock file in the same directory. Write the ledger atomically under that lock before disabling. Keep records through process failure, but expire their authority to mutate when the GUI session or boot changes. Reconcile entries already verified active, including after rollback or manual recovery, and retain entries when state is uncertain. Otherwise a recoverer can miss the only record of the disabled display, or old entries can cause repeated recovery failures. 6. **P2 · correctness — The plan leaves paths around the HDMI opt-in and omits the incident from the completion gate.** Task 10 Step 4 still directs the user to run the script without the dependency claimed in the brief. The script also disables the external display again to prepare the final-display refusal test, so gating only the named HDMI test would leave another path to the same mutation. Gate every external disable, including test setup, behind the internal pass and explicit opt-in. Make the macOS 27 matrix require observed recovery from the HDMI disappearance for any claim that it is supported, plus an unattended timeout run that restores a usable screen. A successful internal round trip alone can satisfy the current brief. ## P3 and P4 findings

7. **P3 · correctness — The acceptance tests reward a saved-ID call and miss important outcomes.** The existing fake is explicitly configured to restore a missing display when called with its old ID. The proposed test can therefore pass by construction, and it can accidentally exercise the already successful immediate rollback instead of recovery by a later invocation. Require an initially unsuccessful rollback, then assert that the later invocation restores the intended UUID. Add cases where the old ID belongs to another display, the same UUID reappears with a new ID, and enable returns success without restoring the target. A stubbed script run can exercise no input, late confirmation, and a slow mutation, with hardware verification reserved for actual display recovery. [phase-1.1-brief.md:33](/docs/phases/phase-1/phase-1.1-brief.md:33) · [ConnectionControllerTests.swift:224](/Tests/DisplayControlCoreTests/ConnectionControllerTests.swift:224) · [ConnectionControllerTests.swift:340](/Tests/DisplayControlCoreTests/ConnectionControllerTests.swift:340)

8. **P4 · architecture — Phase 2 needs the recovery logic below the CLI policy.** `connect all` returns failure if any candidate fails, even when a usable screen has been restored. Phase 2 must determine whether the active count is still zero immediately before recovery, then verify that at least one screen became active. If the future agent checks the count and calls unconditional `connectAll()` separately, it can override an intentional display choice when a screen returns between those operations. Keep identity validation and reconnect outcomes in `DisplayControlCore` so the later agent can recheck the zero-display condition under the operation lock and evaluate the result independently of CLI exit status.
